# 文档写作契约

公开文档是用户和 Agent 都可能照着执行的产品说明。文档应描述当前产品怎样工作，不复述本次修改过程，也不把设想写成已经实现的能力。

## 先确认事实

- 命令、参数和默认值以当前 CLI、Schema、源码和测试为准。历史记录只能说明当时发生了什么，不能代替当前实现。
- 不根据目录名推断审核、执行或同步状态。文件位于 `wiki/` 不一定有审核记录，文档引用 Skill 不表示 Skill 已运行，关联团队库也不表示文件已经同步。
- 明确区分查询命中、实际使用、人工审核和任务完成。它们是不同事件，不能互相证明。
- `partial`、`failed`、`skipped`、`SIMULATED` 和 `REPLAYED` 保持原义。后续产生了摘要或成功结果，也不能回写成另一种状态。

## 页面职责

- 首页回答 OKS 解决什么问题，并把读者带到一条可以验证的首次使用路径。
- 入门页解释必要概念和预期结果。不要把维护命令、内部协议和所有可选能力提前塞给新用户。
- 使用页按任务组织：用户想做什么，交给 Agent 什么信息，结果保存在哪里，怎样检查，失败后看哪里。
- Concepts 解释对象、状态和工作原理。Reference 提供准确命令、字段、协议与限制。维护者页面记录实现约束和验证方法。
- 案例必须区分教程样例、模拟结果和实际运行记录。截图只能证明画面中可见的状态。

## 术语

- `Agent` 保持英文，不作中文翻译。首次出现时可以补一句职责说明，例如“Agent 负责理解任务并调用 OKS”。
- `Raw` 是来源、原文、提取结果和处理状态。`Raw Bundle` 是标准材料包，不是知识结论。
- `Candidate` 是待审核提议，通常保存在 `drafts/`；`Draft` 是目录和部分 CLI、界面沿用的名称，不要把它写成另一种内容状态。
- `Wiki` 是 `wiki/` 中的知识页，不是一概“已审核知识”。只有存在有效审核记录时，才能说明某个版本经过审核；审核也不保证内容永远正确。
- 面向用户统一使用“查询”。在解释命令和算法时，可以说明 `Recall` 是对应的产品和命令名称，“检索”指匹配与排序过程。不要在同一段落中随意轮换“查找、检索、召回、查询”。
- `Skill`、`Hook`、`CLI`、`Studio`、`Profile`、`Goal` 和 `Trace` 保留产品名称，并用一句中文解释职责。不要用“操作指南”“自动触发设置”“运行记录”等中文替代产品名称。
- 术语的完整定义见[术语表](../concepts/glossary.html)。页面需要首次解释，但不要各自发明另一套说法。

## 写清职责和结果

- 写明主语。用户负责提供目标和审核决定；Agent 负责理解任务、阅读材料和调用工具；CLI 负责校验、保存和查询；Studio 提供本地界面。
- 写明动作的输入、产物和检查方法。例如，直接写“保存来源，生成 Candidate，用户审核后再写入 Wiki”。
- 命令会修改什么、不会修改什么，都应落到具体文件、记录或状态。不要用抽象口号代替可以检查的结果。
- 不用“真实、完整、专业、可靠”代替证据。说明运行了什么检查、观察到什么结果、还有哪些范围没有覆盖。
- 必要的英文术语在第一次出现时直接解释。技术页可以保留字段名和协议名，但不能要求读者靠猜测理解它们。

## 提示词和案例

- 可以提供交给 Agent 的示例请求，但不要虚构 Agent 已经执行或返回的结果。
- 案例按“遇到什么事、提供什么信息、在哪里检查结果、下一步做什么”组织。步骤之间要有因果关系，不为了凑结构强行分成固定数量。
- 不使用未经测量的时间承诺和“一键完成”。截图、本机路径、用户名、凭据和私人界面在提交前必须检查和清理。
- 删除或移动页面前，检查入链、锚点、导航和 GitHub Pages 路由。
