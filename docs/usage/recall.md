# 查询与引用

Recall 根据当前问题返回可能相关的内容。它解决的是“去哪里找”，不直接回答“内容是否正确”或“能否用于当前任务”。Agent 需要继续读取结果、核对范围，再决定怎样引用。

```text
请查找当前任务相关的知识，打开条目和来源再回答我的问题；
说明用了哪些内容，哪些可能过时；证据不足时指出缺口。
```

## Recall 查询哪些内容

默认结果分为三条通道：

| 结果字段 | 来源 | 需要怎样理解 |
|---|---|---|
| `episodic` | `raw/` 和当前权限范围内的 `profiles/` | 用于回查来源和背景，不是统一审核过的结论 |
| `knowledge` | 当前个人库的 `wiki/` | 包含可查询 Wiki；可能有 `active`、`provisional` 或 `stale` 页面 |
| `team_knowledge` | 已关联团队库中符合准入条件的知识 | 只读返回，并保留团队库与 Git 修订来源 |

`--knowledge-only` 只关闭 `episodic`，不会关闭 `team_knowledge`。执行记录、Mail 和 Registry 不属于普通 Recall 结果。

用户 Profile 和项目 Profile 需要相应的用户或项目范围才会参与查询。当前 Goal 可以影响排序，但不会改变 Wiki 的审核状态。

## 怎样提出更容易查询的问题

说明任务、项目、版本、时间和预期输出。例如：

```text
在项目甲 2.4 版本提交“导出失败”的问题报告前，需要准备哪些信息？
```

这比“这个问题怎么办”更容易匹配到适用范围准确的内容。新 Session 中还应确认连接的是同一个知识库；同名文件夹或相同问题不代表使用了同一个实例。

## 怎样检查 Wiki 结果

Wiki 命中不等于已经审核。Agent 应查看：

- `status`：`provisional` 是暂定内容，`stale` 表示可能过时，`active` 表示处于正常使用状态；
- `human_reviewed_at`：存在时说明某个版本经过人工接受；
- 来源和关系：页面由哪个 Candidate 或 Raw 支持，是否补充、质疑或取代其他页；
- 适用范围：项目、版本、日期和前置条件是否与当前任务一致。

排名和 `relevance` 只表示检索匹配程度。页面的记忆 `score`、使用次数和 `confidence` 也不能代替来源与审核判断。

## 查询、注入、采用和审核不同

| 事件 | 表示什么 | 会不会改变审核状态 |
|---|---|---|
| Recall 命中 | 查询找到了页面 | 不会 |
| Hook 注入 | 宿主把结果提供给 Agent | 不会 |
| Agent 引用 | 回答或方案使用了页面内容 | 不会 |
| `oks wiki use` | 明确记录页面被实际采用 | 不会，只更新使用信号 |
| Candidate Promote | 人接受了具体版本 | 会生成带审核记录的 `active` Wiki |

因此，回答与某页内容相似不能证明 Agent 查询过 OKS；搜索命中也不能证明 Agent 实际采用了它。需要核对时，让 Agent 展示命中项和回答中对应使用的位置。

## 没有结果或结果不合适

依次检查：

1. 当前知识库是否正确；
2. 内容是否只存在于 Candidate，尚未进入 Wiki；
3. 页面是否已 `dropped`、`superseded` 或归档；
4. 问题中是否缺少项目、版本或同义表达；
5. 团队库是否已关联到正确的已提交修订；
6. 检索后端是否发生降级，过滤原因是什么。

如果结果相互冲突，不要只取排名最高的一条。应展示各自范围和来源，必要时补充材料并提出新的 Candidate。

## 可选的自动 Recall

Hook 可以在支持的宿主事件上自动运行查询。默认 Prompt Hook 注入的是个人 Wiki 的 `knowledge` 结果，不等同于手工 `oks recall` 的全部三条通道。短提示、低于阈值的结果或冷却期内重复页面可能被跳过。

没有 Hook 时，直接要求 Agent 执行 Recall 即可。启用情况用 `oks hook status` 检查，不要根据一次回答的内容猜测 Hook 已正常运行。

技术细节见[召回引擎](../algorithms/recall-engine.html)和[CLI 参考](../reference/cli.html)。发现旧知识需要处理时，阅读[修订、替代与归档](maintain.html)。
