# 收录材料

收录的目标是保存一份可回查的来源，而不是立即生成结论。Raw 应包含原文或实际取得的内容、出处、提取过程和处理状态。是否再整理 Candidate，取决于材料是否支持可复用的判断。

## 交给 Agent 什么

提供文件、链接或文本，并说明它与哪个问题、项目或时间范围有关。范围越具体，Agent 越不容易把局部做法写成通用规则。

```text
请收录我提供的这份材料，先查找同主题的已有知识，保存来源和原文，
区分来源主张与推断，提出待审核知识，并告诉我保存了什么、缺少什么。
```

例如：“这是项目甲 2.4 版本的发布复盘，请保留故障经过，并整理下次发布前可复用的检查项。”这比“把这篇文章存一下”更容易得到范围准确的 Candidate。

## Agent 会做什么

1. **确认知识库和已有内容**：避免把同一来源重复保存，也检查是否已有相关 Wiki 或 Candidate。
2. **识别材料类型**：文本可直接读取；PDF、扫描件、音视频或平台链接可能需要额外的提取能力。
3. **保存 Raw**：记录来源、实际取得的内容、附件或转换产物，并保留处理状态。
4. **检查证据是否足够**：区分来源作者的主张、原始事实和 Agent 的推断。
5. **按需提出 Candidate**：只有存在值得复用且有依据的内容时，才写入 `drafts/`。

`oks ingest prepare`、`oks ingest run` 和 `oks raw-commit` 负责准备、采集、校验和组装材料。它们不会自行生成 Candidate，也不会批准或写入带审核记录的 Wiki。

## Raw 与 Candidate 的区别

| 内容 | 保存位置 | 回答的问题 |
|---|---|---|
| Raw | `raw/` | 来源里实际有什么，内容怎样取得，哪些部分缺失 |
| Candidate | `drafts/` | 哪些判断或做法可能值得复用，依据和适用范围是什么 |

两者不必同时产生。只保存材料是有效结果；证据不足时，先补来源比勉强生成 Candidate 更合适。

## 处理不同材料时注意什么

- **网页**：记录原始 URL、取得时间和实际保存的正文。登录墙或动态内容可能只能得到部分结果。
- **PDF 和扫描件**：核对页码、表格、图片和公式是否被提取；OCR 结果可能有错。
- **音视频**：区分平台字幕、用户提供的转写和本地 ASR；人名、数字和术语需要抽查。
- **Office 文档**：确认批注、表格、图片或嵌入对象是否在当前处理能力范围内。
- **远程 Provider**：使用前说明数据会发送到哪里、需要哪些凭据和费用；按实例策略决定是否允许。

不要把 Agent 对材料的摘要覆盖到原始提取结果上。原文、转换产物和后续解释应能分别找到。

## 怎样理解处理状态

| 状态 | 含义 | 接下来怎么做 |
|---|---|---|
| 成功 | 计划中的步骤完成 | 抽查保存内容和来源 |
| `partial` | 只完成了一部分 | 说明缺失范围，判断是否仍足以提出 Candidate |
| `failed` | 相应步骤失败 | 保留错误和已产生的证据，修复后重试 |
| `skipped` | 相应步骤被跳过 | 说明原因，不把它写成成功 |

一个阶段成功，不会覆盖其他阶段的失败。例如音频转写成功，但关键帧提取失败，最终记录仍要保留两种状态。

## 完成后检查

- Raw 能回到原文、附件或实际提取结果，并能看到出处。
- 缺页、缺附件、未识别图表或未转写片段有明确说明。
- Candidate 中的每个重要判断都能指向证据，并保留适用范围。
- Agent 的推断没有被写成来源原话。
- 没有在你审核前把 Candidate 称为已审核知识。
